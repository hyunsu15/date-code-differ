# 폴더 구조 가이드 — Colocation과 모듈 경계

폴더 구조의 목표는 "예쁜 트리"가 아니라 **변경 비용을 낮추는 것**이다.
함께 변경되는 코드는 가까이 두고(colocation), 모듈 경계는 도구로 지키고, 의존 방향은 한 방향으로 흐르게 한다.

관련 문서: [코딩가이드.md](코딩가이드.md)의 "폴더를 나누는 기준은 응집성" 절의 확장판이다.

---

## 0. 용어 정의

논쟁을 막기 위해 먼저 용어를 고정한다.

| 용어 | 의미 |
|------|------|
| **이동(colocation 해제)** | 특정 기능 폴더 안에 있던 파일을 그 폴더 밖으로 빼는 모든 행위 |
| **승격(promotion)** | 모듈을 `shared/`(또는 `common/`) 같은 전역 계층으로 올려 여러 기능이 공식적으로 의존하게 만드는 행위 |
| **공개 API** | 폴더의 `index.ts`가 export하여 외부 사용을 허용한 표면(surface) |

승격은 이동의 특수한 경우다. **이동 중에서 목적지가 전역 계층인 것**을 승격이라 부른다.

---

## 1. 컴포넌트 근접성의 원칙 (Colocation)

특정 컴포넌트나 함수에서만 사용하는 하위 컴포넌트, 스타일, 유틸리티, 테스트 코드는 **그것을 사용하는 코드와 최대한 가까운 위치**에 둔다.

### 기본 규칙 — Rule of Three

- **1번째 사용처**: 사용하는 곳 바로 옆에 둔다.
- **2번째 사용처가 생기면**: **복사(중복)를 허용한다.** 아직 추상화하지 않는다. 단, **복사할 때 원본 경로를 주석으로 남긴다.** 이 표시가 없으면 3번째 사용처가 생겨도 아무도 알아채지 못해 중복이 영구화된다.
- **서로 다른 기능(feature) 3곳에서 쓰이게 되면**: 승격을 **검토**한다. (5번 참고) 같은 feature 안에서 3곳에 쓰이는 것은 승격 사유가 아니다 — 그 feature 내부에서 위치만 정리한다.

두 번 쓰인다고 바로 `shared/`로 올리면, 우연히 코드가 비슷했을 뿐인 두 기능이 하나의 추상화에 묶여버린다. **잘못된 추상화는 중복보다 비싸다.**

### 예외

디자인 시스템, 라우팅, 인증, API 클라이언트 등 **명백한 공통 인프라/횡단 관심사**는 처음부터 shared 영역에 둘 수 있다.

## 2. 의존 방향 규칙 (Layer Direction)

구조가 무너지는 가장 흔한 경로는 deep import가 아니라 **feature 간 수평 참조 → 순환 의존**이다.

### 규칙

의존 방향은 항상 **단방향**이다.

```
app / pages   (조합 계층)
    ↓
features      (기능 계층)
    ↓
shared        (공통 계층)
```

- `features/payment → features/order` 같은 **feature 간 직접 참조를 금지**한다.
- 금지 대상은 **feature 간 수평 참조**다. `shared/` 내부에서 모듈끼리 참조하는 것(예: `shared/ui`가 `shared/lib` 사용)은 정상이며 금지하지 않는다.

### feature A가 feature B를 정말 필요로 할 때

금지만 하면 개발자는 몰래 수평 import를 한다. 해결책을 함께 제공한다. 우선순위 순:

1. **(기본값) 상위 계층에서 조합한다.** page/app 계층이 두 feature를 모두 import해서 연결한다.
2. **공유 로직을 shared로 내린다.** 단, Rule of Three와 5번 승격 조건을 만족할 때만. **feature 2곳이 공유한다는 것만으로는 부족하다** — 그 시점은 아직 "2번째 사용처"이므로 1번의 "복사 허용" 원칙이 우선한다.
3. **인터페이스/이벤트로 역전한다.** feature가 인터페이스만 정의하고, 구현 연결은 상위 계층이 담당한다.

## 3. 디렉터리 가시성 제어 (Public API / Encapsulation)

폴더 외부에서는 하위 구현 파일에 직접 접근하지 않고, 해당 폴더의 `index.ts`를 통해 공개된 API만 사용한다.

```ts
// pages/checkout에서 — 허용 (상위 계층이 공개 API를 통해 사용)
import { PaymentService } from '@/features/payment';

// pages/checkout에서 — 금지 (deep import)
import { InternalCalculator } from '@/features/payment/internal-calculator';

// features/order에서 — 금지 (공개 API를 통해도 feature 간 수평 참조는 2번 위반)
import { PaymentService } from '@/features/payment';
```

**목적**: 내부 구조 변경이 외부 의존성에 전파되지 않도록 한다.

### 규칙은 도구로 강제한다

deep import 금지는 사람이 지키는 규칙이 아니다. IDE 자동완성이 deep import를 먼저 제안하기 때문에, lint 없이는 반드시 위반이 쌓인다.

- ESLint `no-restricted-imports` 또는 `eslint-plugin-boundaries`
- 대규모라면 `dependency-cruiser`로 순환 의존까지 CI에서 차단

### barrel(index.ts)의 범위 제한

barrel 파일은 공짜가 아니다. 폴더마다 만들면 다음 비용이 발생한다:

- Vite/Next dev 서버 성능 저하
- tree-shaking 방해
- 순환 import 유발

따라서 **barrel은 feature 최상위 경계에만 둔다.** feature 내부 폴더까지 `index.ts`를 강제하지 않는다.

## 4. 구조 리팩토링 트리거

다음 조건은 분리를 "강제"하는 규칙이 아니라, **재구성을 검토하는 신호**다.

### 분리를 검토하는 신호

- 폴더 내 파일 수가 7개 이상이 될 때 (참고용 숫자)
- 특정 하위 관심사를 나타내는 파일군이 3개 이상 생길 때 (참고용 숫자)
- **한 변경 요청에서 같은 폴더의 서로 다른 책임이 반복적으로 함께 수정될 때** ← 실제 변경 이력에 기반한 증거이므로 가장 신뢰할 만한 신호

### 역방향 신호 — 합치기를 검토하는 신호

- **같은 기능을 수정하는데 매번 여러 폴더를 건드려야 할 때** (Shotgun Surgery) → colocation이 깨졌다는 신호

파일이 7개를 넘어도 응집도가 높으면 쪼개지 않는 것이 맞는 경우가 많다. 숫자보다 **변경 이력**을 믿는다.

---

## 5. 전역 승격 조건

**서로 다른 상위 기능 3곳 이상**에서 동일한 책임의 모듈이 반복 사용될 때, `shared/`(또는 `common/`)로의 승격을 검토한다. (1번의 Rule of Three와 같은 기준이다: **서로 다른 기능에서의** 3번째 사용처 = 승격 검토 시점)

승격 전 확인할 것:

- 단순한 **문법 유사성**이 아니라 **동일한 책임**인가?
- 인터페이스가 **안정**되어 있는가? (승격 후에도 사용처마다 다른 요구로 계속 바뀔 것 같다면 아직 이르다)

## 6. 점진적 도입

이 문서의 장치들은 전부 유지비용이 있다. 코드베이스 규모에 맞게 단계적으로 도입한다.

| 단계 | 도입 시점 | 도입 내용 |
|------|-----------|-----------|
| 1 | 처음부터 (비용 없음) | colocation + Rule of Three — 규칙만으로 충분 |
| 2 | feature가 여러 개 생기고 팀원이 늘 때 | lint 경계: deep import 금지, 레이어 방향 규칙 |
| 3 | 규모가 커지고 순환 의존이 실제로 발생할 때 | `dependency-cruiser`로 순환 의존 CI 차단 |

작은 코드베이스에서 3단계 장치를 전부 켜는 것은 순손실이다.

## 7. 코드 리뷰 체크리스트

### 도구로 자동화한다 (사람이 리뷰하지 않는다)

- 외부가 폴더 내부 구현 파일을 직접 import하는가 → **lint가 차단**
- feature 간 수평 참조가 있는가 → **lint / dependency-cruiser가 차단**

### 사람이 리뷰한다 (자동화 불가능한 판단)

- 이 파일을 수정할 때 관련 파일이 같은 폴더에 모여 있는가?
- 이 유틸/컴포넌트는 정말 3곳 이상에서, **동일한 책임**으로 쓰이는가?
- 이 폴더의 `index.ts`가 노출하는 공개 표면이 **최소**인가? (무엇을 public으로 둘지는 설계 판단이므로 lint로 잡을 수 없다)
- 이 폴더 안에 서로 다른 책임이 섞여 있지 않은가?

사람의 리뷰 에너지는 응집도·책임 판단처럼 자동화가 불가능한 곳에 쓴다.
