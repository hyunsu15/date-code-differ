# API 성능 가이드

## 1. 필요한 데이터만 응답하기

응답 크기가 커질수록 다음 비용이 증가한다.

* 네트워크 비용 증가
* 직렬화/역직렬화 비용 증가
* 프론트 렌더링 비용 증가

### 안 좋은 예

```json
{
  "id": 1,
  "name": "Kim",
  "createdAt": "...",
  "updatedAt": "...",
  "deleted": false,
  "internalCode": "A001",
  "debugInfo": "...",
  "profileImageBinary": "..."
}
```

### 좋은 예

```json
{
  "id": 1,
  "name": "Kim"
}
```

### 권장 방식

* DTO 분리
* 화면별 응답 모델 사용
* 내부 컬럼 숨기기

## 2. N+1 문제 방지

### 문제 상황

게시글 100개 조회 후 작성자 조회를 100번 추가 수행한다.

* 게시글 조회 1번
* 작성자 조회 100번

### 해결 방법

* JOIN FETCH
* batch size
* projection 사용
* 필요한 경우에만 Lazy Loading

### 예시

```sql
SELECT p.*, u.*
FROM post p
JOIN user u ON p.user_id = u.id
```

## 3. 페이지네이션 적용

대량 데이터 전체 조회 금지.

### 안 좋은 예

```text
GET /posts
```

### 좋은 예

```text
GET /posts?page=1&size=20
```

### 추가 권장

* 최대 size 제한
* **대량 목록 API의 기본은 keyset/cursor 방식으로 한다.** offset 방식(`OFFSET n LIMIT m`)은 앞의 n개 행을 읽고 버리는 구조라 페이지 깊이에 비례해 비용이 증가한다(≈ O(n)). 이는 무한 스크롤 여부와 무관한 구조적 성능 문제다. offset 방식은 총 페이지 수 표시가 필요한 관리 화면 등 제한적 용도로만 쓴다.

### Cursor Pagination 예시

```text
GET /posts?cursor=120
```

## 4. 응답 압축 사용

HTTP 압축 사용.

* gzip / brotli 활성화
* JSON 응답 크기 감소 (전송 크기를 줄임)
* 주의: 동적 응답 실시간 압축은 CPU 비용으로 TTFB가 늘 수 있어 트레이드오프가 있다. 정적 자산은 사전 압축(pre-compressed)이 유리하며, 동적 API는 응답 크기 대비 압축 비용을 실측해 판단한다.

일반적으로 효과가 큰 경우

* 리스트 응답
* 긴 JSON
* 반복 문자열이 많은 경우

## 6. 데이터베이스 조회 최적화

응답 느림의 대부분은 DB 문제.

### 체크리스트

* 인덱스 존재 여부
* Full Scan 발생 여부
* 정렬 컬럼 인덱스 여부
* `LIKE '%keyword%'` 사용 여부 (앞에 `%`가 오면 B-tree 인덱스를 탈 수 없어 풀스캔 → Full-Text Search 검토)
* 불필요한 DISTINCT 여부

반드시 확인

* EXPLAIN PLAN

## 7. 클라이언트 요구 기반 응답 설계

응답은 화면이 실제로 사용하는 데이터에 맞춰 형태를 잡는다(shaping). 단, "화면 수만큼 엔드포인트를 만든다"는 의미가 아니라 "응답을 화면 요구에 맞게 다듬는다"는 의미다.

> 도메인 API는 리소스 중심으로 안정적·재사용 가능하게 유지한다(`Restapi가이드.md` 기준). UI는 도메인보다 자주 바뀌므로, 화면을 API 계약에 직접 결합하면 백엔드가 UI 변경에 끌려다니게 된다.

### 안 좋은 방식

* 범용 API 하나로 모든 화면 처리 → over-fetching 또는 다중 호출(chatty) 유발
* 화면마다 전용 엔드포인트를 양산 → 엔드포인트 폭발, UI-백엔드 강결합, 재사용성 저하

### 좋은 방식

* **필요한 데이터만 응답** — 필드 선택(sparse fieldset, 예: `?fields=id,name`)으로 클라이언트가 받을 필드를 고른다.
* 화면 맞춤 조합이 필요하면 **BFF(Backend For Frontend) 계층**이나 **조회 전용 집계(read model) 엔드포인트**로 처리한다. 핵심 도메인 API는 그대로 두고 프레젠테이션 계층에서 조합한다.
* (대안) 필드 선택·조합 요구가 많다면 **GraphQL** 같은 필드 단위 질의도 검토한다.
