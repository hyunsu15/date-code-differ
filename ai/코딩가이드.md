# 규칙 : else 최소화

## 목적

중첩을 줄이고 코드의 흐름을 단순하게 만든다.

## 권장 방식

### Bad

```ts
if (user) {
  return user.name;
} else {
  throw new NotFoundException();
}
```

### Good

```ts
if (!user) {
  throw new NotFoundException();
}

return user.name;
```

## 장점

* 들여쓰기 감소
* 가독성 향상
* 예외 상황을 먼저 처리
* 코드 흐름이 직관적

## 실무 적용

* Guard Clause(Early Return) 적극 활용
* else 없이 표현 가능하면 제거
* 단순한 조건 분기는 무리하게 제거할 필요 없음

# 규칙 : 중요한 원시값 포장하기

## 목적

의미 있는 도메인 데이터를 단순 문자열이나 숫자가 아닌 객체로 표현한다.

## 권장 방식

### Bad

```ts
createUser(email: string)
```

### Good

```ts
class Email {
  constructor(private readonly value: string) {
    this.validate(value);
  }

  private validate(email: string) {
    // 이메일 검증
  }
}

createUser(email: Email)
```

## 장점

* 도메인 의미가 명확해짐
* 검증 로직 집중 가능
* 잘못된 값 사용 방지
* 타입 안정성 향상

## 적용 대상 예시

* Email
* PhoneNumber
* UserId
* Money
* Password
* OrderNumber

## 실무 적용

모든 원시값을 포장할 필요는 없다.

비즈니스 규칙이 존재하거나 검증이 필요한 값에만 적용한다.

# 규칙 : 클래스를 작게 유지하기

## 목적

하나의 클래스가 너무 많은 책임을 가지지 않도록 한다.

## Bad

```ts
class UserService {
  validate() {}
  save() {}
  sendEmail() {}
  generateReport() {}
  createExcel() {}
}
```

## Good

```ts
class UserValidator {}

class UserRepository {}

class UserNotificationService {}

class UserReportService {}
```

## 장점

* 책임 분리
* 테스트 용이
* 변경 영향 최소화
* 유지보수성 향상

## 실무 기준

다음과 같은 신호가 보이면 분리를 고려한다.

* 메서드 수가 과도하게 많음
* 클래스가 여러 이유로 변경됨
* 파일 크기가 지나치게 큼
* 이름이 모호해짐

## 권장 기준

* 하나의 명확한 책임
* 파일 크기보다 역할에 집중
* SRP(Single Responsibility Principle) 준수

# 규칙 : 복잡한 컬렉션은 일급 컬렉션 사용

## 목적

컬렉션을 단순 배열이 아니라 도메인 객체로 다룬다.

## Bad

```ts
const users: User[] = [];
```

여러 곳에서 배열을 직접 조작하게 된다.

## Good

```ts
class Users {
  private readonly users: readonly User[];

  constructor(users: User[]) {
    this.users = [...users]; // 방어적 복사: 외부 배열 변경이 내부 상태를 오염시키지 않게 한다
  }

  findById(id: number): User | undefined {
    return this.users.find((u) => u.id === id);
  }

  getActiveUsers(): readonly User[] {
    return this.users.filter((u) => u.isActive);
  }

  add(user: User): Users {
    return new Users([...this.users, user]); // 불변: 새 인스턴스를 반환한다
  }
}
```

`readonly User[]`(=`ReadonlyArray<User>`)로 선언하면 클래스 내부의 `push` 등 변경도 컴파일 오류로 잡힌다. (기존 `User[]`는 참조 재할당만 막는다.) 생성자에서는 전개 구문(`[...users]`)으로 로컬 가변 배열을 만든 뒤 `readonly` 필드에 한 번만 할당하므로 타입 오류 없이 컴파일된다. 변경이 필요한 경우 항상 새 인스턴스를 반환하는 방식으로 처리한다.

## 장점

* 컬렉션 관련 로직 집중
* 중복 코드 감소
* 도메인 표현력 증가
* 무분별한 배열 조작 방지

## 적용 대상 예시

* Users
* Orders
* Products
* DiscussionMessages
* ScenarioResults

## 실무 적용

단순 CRUD 수준의 배열은 굳이 감쌀 필요가 없다.

다음과 같은 경우 적용을 고려한다.

* 조회 로직이 반복됨
* 필터링 규칙이 많음
* 비즈니스 규칙이 포함됨
* 컬렉션 자체가 중요한 도메인 개념임

# 실무에서 중요하게 생각하는 설계 원칙

## 개요

좋은 코드는 단순히 객체지향 원칙을 잘 지킨 코드가 아니다.

실제 운영 환경에서는 다음 두 가지가 특히 중요하다.

1. 테스트 가능한 코드
2. 인프라에 종속되지 않는 도메인

이 문서는 해당 원칙들을 정리한다.

---

# 1. 테스트 가능한 코드 작성하기

## 목적

비즈니스 로직을 쉽고 안정적으로 검증할 수 있도록 만든다.

테스트가 어려운 코드는 변경에 대한 두려움을 만들고 유지보수 비용을 증가시킨다.

---

## 피해야 할 패턴

### 시간 직접 조회

```ts
const isExpired = coupon.expiredAt < new Date();
```

함수 내부에서 현재 시간을 직접 가져오면 테스트가 어려워진다.

---

### 랜덤값 직접 생성

```ts
const token = Math.random().toString();
```

---

### 비즈니스 로직 내부에서 환경 변수 직접 참조

진입점(entry point)이나 config 모듈에서 한 번 읽어 주입하는 것은 정상이다. 비즈니스 로직 내부에서 직접 참조하는 경우가 문제다.

```ts
// 비즈니스 로직 내부에서 직접 참조하는 경우 — 피해야 할 패턴
const apiKey = process.env.API_KEY;
```

---

### 외부 시스템 직접 호출

```ts
await emailService.send();
```

---

## 권장 방식

외부 의존성을 주입받는다.

### 예시

#### 시간 주입

```ts
function isCouponExpired(
  expiredAt: Date,
  now: Date,
): boolean {
  return expiredAt < now;
}
```

테스트 시

```ts
isCouponExpired(
  new Date('2026-01-01'),
  new Date('2025-12-31'),
);
```

처럼 원하는 시점을 자유롭게 검증할 수 있다.

---

#### Clock 추상화

```ts
interface Clock {
  now(): Date;
}
```

```ts
class SystemClock implements Clock {
  now() {
    return new Date();
  }
}
```

서비스에서는 Clock만 의존한다.

```ts
class CouponService {
  constructor(
    private readonly clock: Clock,
  ) {}

  validate(coupon: Coupon) {
    return coupon.expiredAt > this.clock.now();
  }
}
```

---

## 장점

* 테스트 작성이 쉬움
* 예외 상황 검증 가능
* 시간에 의존하지 않음
* 랜덤성 제거 가능
* 변경에 강함

---

## 실무 체크리스트

다음 코드가 보이면 한 번 의심해본다.

```ts
new Date()
Date.now()
Math.random()
process.env
```

비즈니스 로직 내부에서 직접 사용 중이라면 추상화 가능성을 검토한다.

# 2. 인프라의 노예가 되지 않기

## 목적

비즈니스 규칙이 특정 기술에 종속되지 않도록 만든다.

도메인 모델은 데이터베이스나 프레임워크보다 오래 살아남는다.

---

## 피해야 할 패턴

도메인 객체가 인프라 기술에 오염되는 경우

```ts
@Entity()
export class User {
  @Column()
  name: string;

  @Column()
  email: string;
}
```

처음에는 편하지만 시간이 지나면

* DB 구조
* ORM 정책
* 프레임워크 제약

이 도메인 설계를 결정하게 된다.

---

## 권장 방식

### 도메인

```ts
export class User {
  constructor(
    private readonly name: string,
    private readonly email: Email,
  ) {}

  changeEmail(email: Email) {
    ...
  }
}
```

---

### 영속성 모델

```ts
@Entity()
export class UserEntity {
  @Column()
  name: string;

  @Column()
  email: string;
}
```

---

### Repository에서 변환

```ts
UserEntity
  ↔
User
```

변환 책임을 분리한다.

---

## 장점

* ORM 교체 가능
* 테스트 용이
* 도메인 순수성 유지
* 비즈니스 규칙 집중 가능

---

## 현실적인 타협

Controller → Service → Repository 이라면, 해당 방향의 의존성만 허용하며, 하위 계층에서 상위 계층을 참조하지 않는다.

모든 프로젝트에서 완벽한 DDD 구조가 필요한 것은 아니다. 

단순 CRUD 프로젝트라면

```txt
Controller
 ↓
Service
 ↓
Repository
```

정도로도 충분하다.

하지만 다음 조건에 해당한다면 도메인 분리를 고려한다.

* 결제
* 주문
* 정산
* 포인트
* 쿠폰
* 재고
* 승인 프로세스

즉, 비즈니스 규칙이 복잡해지는 순간이다.


---


## 테스트 가능한 코드

비즈니스 로직이

* 현재 시간
* 랜덤값
* 환경 변수
* 외부 시스템

에 직접 의존하지 않도록 만든다.

---

## 인프라 독립적인 도메인

비즈니스 규칙은

* 데이터베이스
* ORM
* 프레임워크

보다 더 오래 살아남는다.

도메인이 기술을 의존하는 것이 아니라,
기술이 도메인을 지원하도록 설계한다.

# 안 쓰는 것은 정리한다.

git으로 코드 관리하기에 안 쓰는 코드, 의존성, import가 있다면, 정리한다.

# 양방향 의존성이 보이면, 단방향 의존성이 되게 해라. 특히 패키지(폴더)가 양방향 의존성이 보인다면, 단방향 의존성으로 바꿔라.


# 🛡️ Guard Clause (보호 구문) 가이드

Guard Clause(보호 구문)는 함수의 가독성과 유지보수성을 극대화하기 위해 사용하는 **조기 반환(Early Return) 테크닉**입니다. 예외 상황이나 잘못된 인자가 들어왔을 때, 함수의 입구에서 미리 걸러내고(Guard) 곧바로 종료(Return/Throw)시키는 것이 핵심입니다.

---

## ❌ 안 좋은 예시: If-Else 중첩 구조 (Deep Nesting)

아래 코드는 예외 조건을 확인할 때마다 `if`문 안쪽으로 계속 파고드는 전형적인 패턴입니다.

```typescript
function registerUser(user) {
  if (user !== null) {
    if (user.isValidEmail) {
      if (!user.isAlreadyRegistered) {
        // 💡 실제 핵심 비즈니스 로직이 한참 안쪽에 숨어있음
        const savedUser = db.save(user);
        return savedUser;
      } else {
        throw new Error("이미 가입된 유저입니다.");
      }
    } else {
      throw new Error("이메일 형식이 잘못되었습니다.");
    }
  } else {
    throw new Error("유저 정보가 없습니다.");
  }
}
```
# ✅ 좋은 예시
```ts
function registerUser(user) {
  // 🛡️ Guard Clauses: 예외 상황은 입구에서 즉시 방출!
  if (user === null) throw new Error("유저 정보가 없습니다.");
  if (!user.isValidEmail) throw new Error("이메일 형식이 잘못되었습니다.");
  if (user.isAlreadyRegistered) throw new Error("이미 가입된 유저입니다.");

  // ✨ 메인 스트림: 안전함이 보장된 상태에서 깔끔하게 비즈니스 로직 진행
  const savedUser = db.save(user);
  return savedUser;
}
```

# 타입을 사용할 수 있는 언어라면, 가능한 타입과 리턴을 strict으로. as any, as unknown as 금지한다. 암묵 게약을 타입이 드러낼 수 있도록 한다. 
가능하면 그렇게 하고 안된다면, 무리해서 하지 않는다.

# DDD를 한다면, 다음과 같은 폴더 구조를 사용한다.
```

```

# 폴더를 나누는 기준은 응집성을 기준으로 유기적으로 가져간다.

폴더는 개수나 깊이를 기준으로 나누는 것이 아니라, 함께 변경되는 코드가 함께 위치하도록 구성한다.

> 상세 규칙(Colocation, Rule of Three, 의존 방향, deep import 금지, 승격 조건, 점진적 도입)은 [폴더구조가이드.md](폴더구조가이드.md) 참고.
