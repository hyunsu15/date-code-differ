# 간단히 한 일은 docs/한일/YYYY-MM-DD.md 에 남기기
수정이 완료되면 작업 내역을 기록한다.

경로:
docs/한일/YYYY-MM-DD.md

규칙:
- 사용자의 현재 날짜를 사용한다. 이 날짜는 세션이 시작한 날이 아니라 사용자 시간이다. 이를 작성하기 전에 확인한다.
- 파일이 없으면 생성한다.
- 파일이 있으면 맨 아래에 이어서 작성한다.
- 코드 전체를 붙여넣지 않는다.
- 변경 이유와 결과를 중심으로 작성한다.
- 항목당 1~3줄 이내로 작성한다.
- 외부 API 변경 여부를 반드시 기록한다.


# 테스트 코드 작성한다.

내용은 테스트가이드.md를 참고한다.

# 코드 수정 시 영향도 분석 및 연관 로직 안내한다.
- 수정한 함수를 사용하는 컴포넌트를 확인하여, 컴파일나 로직상 문제가 되지 않는지 확인한다.
- 데이터 구조(DTO, Entity 등) 변경 시, 이를 참조하는 매핑 로직이나 API 컨트롤러도 함께 변경 대상인지 확인한다.


# 사용설명서내용을 만들거나 갱신한다.
- 기술적 전문 용어를 지양하고, 사용자의 눈높이에 맞추어 이해하기 쉽고 명확하게 작성한다.
- 화면 UI 설명이 필요할 경우 스크린샷을 첨부하며, 핵심 기능 강조가 필요할 때는 박스, 화살표 등의 편집(하이라이트)을 통해 직관적으로 안내한다.

캡처할떄는 맥략 유지한다.
- 부가 설명 : 특정 버튼 하나만 덜렁 잘라서 캡처하면 사용자는 "이 버튼이 화면 어디에 붙어있는 거지?" 하고 헤매게 됩니다.
- 해결방법: 화면 전체(혹은 넓은 영역)를 먼저 보여주고, 강조하고 싶은 부분에 빨간색 테두리 박스(ㅁ)나 번호(①, ②, ③)를 매겨서 편집한다.

- 문장을 '행동 중심(Action-oriented)'으로 쪼개기
    - [설정] 메뉴 이동 ➡️ [API 키 발급] 버튼 클릭 ➡️ 생성된 키 복사


# api문서를 갱신한다.
- 직관적이고 간결한 스펙 기술한다.
    -  복잡한 줄글 설명을 지양하고, **[엔드포인트, 파라미터, 데이터 타입, 필수 여부, 예시(Payload)]**를 한눈에 파악할 수 있도록 구조화하여 작성한다.

- 예외 케이스 및 에러 코드 명시한다
    - 정상 응답(200 OK)뿐만 아니라, 발생 가능한 비즈니스 예외 상황(예: 잔액 부족, 권한 없음 등)에 대한 에러 코드와 메시지 샘플을 반드시 누락 없이 최신화한다.

- 설명은 한 줄로, 나머지는 테이블과 JSON 데이터로 대체한다.

- 비즈니스 제약 조건(Validation)을 명확히 작성한다.
    - 데이터 타입만 적지 말고, 제약 조건을 함께 명시하세요.
    - 예시: status (String) ➡️ status (String) [대기: PENDING, 완료: SUCCESS, 실패: FAIL]
    - 예시: title (String) ➡️ title (String)
  
- 실패 스펙도 신경쓴다.
