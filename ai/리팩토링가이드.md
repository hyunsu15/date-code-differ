# 리팩토링 가이드

리팩토링시 다음과 같은 흐름으로 동작한다.

> 성능 개선이 목적이라면 이 가이드가 아니라 `성능개선가이드.md`를 따른다. 성능 개선은 동작·복잡도를 의도적으로 바꾸는 작업이라 동작 보존이 핵심인 리팩토링과 절차가 다르다.

## 리팩토링이란 무엇이고, 무엇이 아닌가

리팩토링은 **관찰 가능한 동작을 바꾸지 않으면서 내부 구조만 개선**하는 작업이다.
반환값·예외·부수효과·순서 등 외부에서 관찰되는 결과가 달라지면, 그것은 리팩토링이 아니라 **동작 변경**이며 별도 작업으로 분리해 사용자에게 보고해야 한다.

이 가이드에서는 성능 변화를 의도적으로 리팩토링 범위 밖(별도 `성능개선가이드.md`)으로 분리해 다룬다. (단, 외부 동작이 동일한 순수 내부 구조 개선은 리팩토링에 해당한다.)

이 원칙은 아래 모든 단계를 관통한다. "더 좋아 보여서" 동작을 손대는 순간 리팩토링이 아니다.

---

# 0. 리팩토링 동기와 범위를 먼저 확정한다.
- 무엇을 왜 개선하는지 명확히 한다. (가독성 / 중복 제거 / 복잡도 감소 중 무엇이 목적인가)
  - 성능이 목적이면 리팩토링이 아니다. `성능개선가이드.md`로 간다.
- 범위 밖의 코드는 건드리지 않는다. 인접 코드를 "겸사겸사" 고치지 않는다. (`개발가이드-카파시가이드.md`의 Think Before Coding · Surgical Changes 참고)
- 목적·범위가 모호하면 추측하지 말고 사용자에게 먼저 확인한다.

---

# 1. 우선 현재 메소드의 일들을 주석으로 명시한다.
- 이 작업은 놓칠 수 있는 요소가 있으니 최소 3번 반복해서 완성도를 올린다.
- 종료 기준: 각 분기·예외·부수효과가 모두 주석에 1개 이상 대응되고, 더 이상 새로 발견되는 동작이 없으면 충분한 것으로 본다. 부족하다고 판단되면 더 반복한다.
- 구현에 대한 세부 내용을 자세히 쓰지 말고, 하는 일을 명시한다.
ex) [잘못된 예시 (구현 세부 내용)]: for문을 돌며 List에서 유저를 찾고 if문으로 정지 상태인지 확인한 뒤 HashMap에 담는다.
[올바른 예시 (하는 일)]: 활성화된 사용자 목록을 조회하여 관리 대상 그룹으로 분류한다.

- 완료 이후에 사용자에게 검토하라고 안내한다.

# 2. Public 메소드 및 Export 메소드를 점검하여, 사용자에게 안내한다.
외부에 공개되는 API는 변경 영향도가 크므로 가장 먼저 확인한다.

각 항목의 구체적 패턴과 Bad/Good 예시는 `코딩가이드.md`(SRP·원시값 포장·일급 컬렉션)와 `개발가이드-카파시가이드.md`(Simplicity First·Surgical Changes)를 기준으로 한다. 아래는 점검 체크리스트다.

## 점검 항목

### 이름이 적절한 책임을 표현하는지

- 메소드명만 보고도 동작을 유추할 수 있어야 한다.
- 이름과 실제 동작이 일치해야 한다.
- 여러 책임을 수행한다면 분리를 고려한다.
- 적절한 책임이 아니라고 판단되면, 사용자에게 제안한다.

### 하나의 명확한 역할만 수행하는지

- 조회, 검증, 저장, 변환 등의 역할이 혼재되어 있지 않은지 확인한다.
- 하나의 변경 이유만 가지도록 설계한다.

### 반환 타입과 파라미터가 의도를 명확하게 표현하는지

- 반환값만 보고도 결과를 이해할 수 있어야 한다.
- 의미 없는 boolean 파라미터 사용을 지양한다.
- 파라미터 수가 많다면 객체로 묶는 것을 고려한다. (단, 시그니처 변경이 수반되므로 순수 리팩토링 범위 밖 — 4장 참고)

### 외부에 노출할 필요가 없는 메소드가 공개되어 있지 않은지

- 사용 범위를 최소화한다.
- private, protected 또는 내부 모듈로 숨길 수 있는지 검토한다.

### 예외 처리 방식이 일관성 있는지

- 동일한 오류를 서로 다른 방식으로 처리하지 않는지 확인한다.
- 예외를 삼키거나 무시하는 코드가 없는지 확인한다.
- 단, 예외 처리 방식의 "개선"은 동작 변경이므로 리팩토링과 분리한다. 여기서는 일관성 문제를 식별해 보고만 한다.

### 사이드 이펙트가 명확한지

- 조회 메소드가 데이터를 수정하지 않는지 확인한다.
- 메소드 이름만으로 예상하지 못한 동작이 없는지 확인한다.

### 테스트하기 쉬운 구조인지

- 외부 시스템 의존성이 과도하지 않은지 확인한다.
- Mock 없이도 테스트 가능한 영역을 늘릴 수 있는지 검토한다.
- 시간, 랜덤값, 외부 API 등의 의존성을 주입받는지 확인한다.

### 호출하는 입장에서 사용하기 쉬운 인터페이스인지

- 사용 방법이 직관적인지 확인한다.
- 암묵적인 호출 순서 의존성이 없는지 검토한다.

## 2-1. 개선 대상(코드 냄새)을 식별한다.
다음 신호가 보이면 리팩토링 후보로 표시한다. 대응 기법은 `코딩가이드.md`를 참고한다.

- 긴 메소드: 한 메소드가 너무 많은 일을 한다. → 메소드 추출 / 들여쓰기 3단계 규칙
- 중복 코드: 같은 구조가 여러 곳에 반복된다. → 공통 추출
- 큰 클래스: 책임이 과도하다. → 클래스 분리(SRP)
- 데이터 뭉치(Data Clumps): 같은 파라미터 묶음이 여러 곳에 함께 등장한다. → 객체로 포장
- 기능 욕심(Feature Envy): 한 메소드가 자기 데이터보다 다른 객체의 데이터를 더 많이 다룬다. → 메소드 이동
- 산탄총 수술(Shotgun Surgery): 하나의 변경이 여러 파일을 동시에 수정하게 만든다. → 응집성 기준으로 재배치
- 원시값 집착: 의미 있는 도메인 값이 string/number로 떠다닌다. → 원시값 포장

# 3. 현재 동작을 보존하기 위한 테스트 코드를 작성한다.
"동작 보존"이란 외부에서 관찰 가능한 모든 결과가 동일함을 의미한다. 다음을 모두 검증한다.

- 반환값 (값뿐 아니라 null / 빈 컬렉션 / Optional 등 경계 의미까지)
- 예외 (종류, 발생 조건, 그리고 호출부가 의존하는 경우 메시지·에러코드)
- 부수효과 (DB·파일·외부 호출뿐 아니라 로그·메트릭·감사 기록의 발생 여부와 내용)
- 이벤트 발생 여부와 발행 순서
- 컬렉션·결과의 순서 및 정렬
- 수치 정밀도·반올림·통화 처리
- 도메인 규칙

테스트는 내부 구현이 아닌 공개 동작을 검증해야 한다. 리팩토링 후 구현이 바뀌어도 테스트가 깨지지 않도록, `테스트가이드.md`의 "출력 행동 검증 · 내부 구현 mocking 금지 · 엣지케이스(빈 입력/null/경계값/동시성/실패 경로)" 원칙을 따른다.

리팩토링 전후로 위 항목이 달라지면 그것은 리팩토링이 아니라 동작 변경이며, 사용자에게 보고해 승인받아야 한다.

## 3-1. 작성한 테스트가 안전망 역할을 하는지 검증한다. (baseline)
- 리팩토링을 시작하기 **전에** 작성한 테스트가 현재 코드에서 모두 통과(green)하는지 먼저 확인한다.
  - 통과하지 못한다면 현재 동작을 잘못 이해한 것이므로 1~3단계를 다시 점검한다.
- 테스트가 실제로 회귀를 잡는지 확인한다.
  - 예: 핵심 분기 하나를 일부러 바꿔 테스트가 실패(red)하는지 확인한 뒤 원복한다.
  - 항상 통과하기만 하는 테스트는 안전망이 아니다.
- 이 baseline 통과 상태를 기준선으로 삼는다. 이후 모든 단계에서 이 기준선이 유지되어야 한다.

> 주의: 테스트는 리팩토링을 시작하기 전에 작성하고 green을 확인한다. 리팩토링 도중 테스트를 함께 수정하면 변경된 동작에 맞춰질 수 있으므로, baseline(사전 green) 확인으로 이를 방지한다.

# 4. Public 및 Export 메소드의 시그니처는 변경하지 않는다.
- 함수명 변경 금지
- 파라미터 변경 금지
- 반환 타입 변경 금지

> 공개 API의 파라미터를 원시값에서 도메인 객체(예: `string` → `Email`)로 강화하고 싶더라도, 이는 시그니처 변경이므로 리팩토링 범위 밖이다. 별도 변경(필요 시 deprecation 절차)으로 분리해 사용자에게 제안한다.

## 4-1. 리팩토링과 기능 변경을 섞지 않는다. (Two Hats)
- 리팩토링 작업 중에는 관찰 가능한 동작(3단계 항목 전부)을 바꾸지 않는다.
- 도중에 버그를 발견하더라도 같은 작업에서 고치지 않는다.
  - `테스트가이드.md`에 따라 버그를 재현하는 테스트를 작성하고 사용자에게 보고하여 선택권을 준다.
- 새 기능·새 동작·새 설정·"유연성"·불가능한 시나리오에 대한 방어 코드를 추가하지 않는다.
  - 모든 변경 라인은 "동작을 보존하는 구조 개선"으로 설명 가능해야 한다.
- 기능 추가/변경이 필요하다고 판단되면, 리팩토링을 먼저 끝내 커밋한 뒤 별도 작업으로 분리한다.

---

# 5. 내부 구현만 개선한다. (한 번에 한 가지씩)
다음 개선을 한꺼번에 적용하지 않는다. 한 가지 변환만 적용한다.

- 중복 제거
- 가독성 향상
- 의존성 정리
- 복잡도 감소

## 5-1. 변경 리듬과 롤백
- 변환 한 가지 → 테스트 실행 → green 확인 → 커밋. 이 리듬을 반복한다.
- 테스트가 red가 되면 새 코드를 디버깅하지 말고, 우선 마지막 green 커밋으로 되돌린 뒤 더 작은 단계로 다시 시도한다.
- 한 번에 하나의 의미 단위만 리팩토링한다. 서로 무관한 변경을 한 커밋에 섞지 않는다.
- 변경 규모가 커지면(리뷰·롤백이 어려워지면) 사용자에게 분할 적용을 제안한다.
- 커밋 메시지는 "무엇을 보존하며 무엇을 바꿨는지"가 드러나게 작성한다.
  ex) refactor: extract validateToken() from auth (no behavior change)

## 5-2. 비기능적 불변식은 보존한다.
테스트로 잡기 가장 어려운 영역이므로 명시적으로 확인한다.

- 트랜잭션 경계(@Transactional 등)의 범위·전파 속성을 변경하지 않는다. 메소드 추출 시 경계가 의도치 않게 분리/병합되지 않는지 확인한다.
- 락 획득 순서, synchronized/락 범위, 원자성 단위를 보존한다.
- 멱등성(idempotency)·재시도 안전성·실행 순서 보장을 유지한다.
- 직렬화 포맷·캐시 키·DB 스키마에 영향을 주는 변경은 리팩토링이 아니다. 배포 중 구/신 버전 공존 호환성도 함께 검토한다.
- 위 항목을 변경해야 한다면 리팩토링이 아닌 별도 변경으로 분리하고 사용자에게 보고한다.

## 5-3. 변경 영향 범위를 전수 확인한다.
시그니처가 같아도 내부 동작 변경은 호출부를 깨뜨릴 수 있다. (`부가내용.md`의 영향도 분석 절차 수행)
- 수정한 함수를 사용하는 컴포넌트를 확인하여 컴파일·로직 문제가 없는지 확인한다.

- 변경한 메소드를 호출하는 모든 위치를 검색하여 나열한다(IDE 참조검색 / grep 등으로 누락 없이).
- 시그니처가 동일해도 반환값의 경계(null/빈 컬렉션), 예외 종류·메시지, 호출 순서 의존성이 바뀌면 호출부가 영향받음을 가정하고 각각 확인한다.
- 데이터 구조(DTO/Entity) 변경 시 이를 참조하는 매핑·컨트롤러·직렬화 지점도 대상에 포함한다.
- 확인 결과를 사용자에게 보고한다.

---

# 6. 작성한 테스트가 리팩토링 후에도 모두 통과해야 한다.
- 리팩토링 전 baseline(3-1단계)과 동일한 결과여야 한다.
- 테스트 결과가 baseline과 달라졌다면 동작이 변한 것이다. 통과시키기 위해 테스트를 고치지 말고 원인을 추적한다.

---

# 7. 완료 후 정리한다.
- 1단계에서 작성한 주석, 관련 문서, 타입 설명이 변경된 구조와 일치하는지 확인하고 갱신한다.
- `부가내용.md` 절차에 따라 변경 이유·결과와 외부 API 변경 여부(순수 리팩토링이면 "변경 없음")를 기록한다.

# 8. 언제 멈출지 정한다.
아래 기준은 리팩토링 진행 중 언제든 적용한다.
- 다음을 달성하면 멈춘다.
  - 식별한 냄새(2-1)가 해소되었고, 6단계 테스트가 모두 통과한다.
  - 요청된 범위의 가독성·중복·복잡도 목표를 만족한다.
