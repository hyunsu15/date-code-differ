# 성능개선 가이드

성능 개선시 다음과 같은 흐름으로 동작한다.

> 구조만 다듬고 동작을 보존하는 작업이라면 이 가이드가 아니라 `리팩토링가이드.md`를 따른다.
> 성능 개선은 속도·자원 사용을 위해 **동작 특성(복잡도·순서·자원 사용)을 의도적으로 바꾸는** 작업이다. 따라서 "동작 보존"이 핵심인 리팩토링과 절차가 다르며, 항상 **측정으로 정당화**되어야 한다.

## 성능 개선이란 무엇이고, 무엇이 아닌가

- 성능 개선은 **측정된 병목**을 근거로, 관찰 가능한 결과(정확성)는 유지한 채 속도/처리량/자원 사용을 개선하는 작업이다.
- 측정 없이 "더 빠를 것 같아서" 코드를 바꾸는 것은 성능 개선이 아니다. 가독성만 해치고 효과가 없거나 오히려 느려질 수 있다.
- 성능 개선은 정확성(반환값·예외·도메인 규칙)을 바꾸지 않는다. 정확성이 바뀌면 그것은 버그이거나 별도의 동작 변경이다.

---

# 0. 추측하지 말고 먼저 측정한다.
- 어디가 느린지 추측하지 않는다. 프로파일링으로 실제 병목(핫스팟)을 찾는다.
- 측정 대상(엔드포인트/함수/쿼리)과 개선 목표를 명확히 한다.
- API 작업이라면 `api-성능가이드.md`의 측정 필수 지표(평균 응답시간 / P95 / P99 / TPS)와 응답 시간 기준표를 사용한다.
- 목적·목표가 모호하면 추측하지 말고 사용자에게 먼저 확인한다.

---

# 1. 개선 전(before) 지표를 기록한다.
- 측정 항목·단위를 명시한다. (예: p95 응답시간 ms, 처리량 req/s, 메모리 MB, 쿼리 수)
- 이 before 값을 기준선(baseline)으로 삼는다. 기준선 없는 "개선"은 검증 불가능하다.

---

# 2. 측정 환경을 고정한다.
재현 불가능한 측정은 노이즈를 개선으로 오인하게 만든다.

- 동일한 입력 데이터, 동일한 하드웨어/설정에서 측정한다.
- 워밍업 후 여러 번 반복 측정하여 평균과 분산(편차)을 본다.
- before와 after는 같은 시점·같은 부하 조건에서 잰다. 가능하면 before→after→before(A-B-A)로 교차 측정해 환경 변동을 걸러낸다.

---

# 3. 정확성을 고정할 테스트를 확보한다.
- 성능 개선은 종종 동작을 건드리므로, 개선 전에 **정확성을 보존하는 테스트**를 확보한다.
  - 검증 대상: 반환값(null/빈 컬렉션 경계 포함), 예외, 순서·정렬, 수치 정밀도, 도메인 규칙. (`테스트가이드.md` 참고)
- 테스트가 현재 코드에서 통과(green)하는지 먼저 확인한다. 이것이 기준선이다.
- 합리적 비용으로 정확성 테스트를 만들 수 없으면, 진행하지 말고 사용자에게 보고한다.

---

# 4. 개선을 적용한다. (한 번에 한 가지씩)
- 한 번에 하나의 최적화만 적용한다. 여러 최적화를 한꺼번에 적용하면 무엇이 효과를 냈는지 알 수 없다.
- 적용할 기법은 `api-성능가이드.md`를 참고한다.
  - 필요한 데이터만 응답 / N+1 방지(JOIN FETCH·batch·projection) / 페이지네이션 / 응답 압축 / DB 조회 최적화(인덱스·EXPLAIN PLAN·Full Scan 점검) / 화면 기준 API 설계
- 최적화를 위해 코드 구조를 먼저 정리해야 한다면, 그 정리는 `리팩토링가이드.md`에 따라 **동작 보존 리팩토링으로 먼저 끝내 커밋**한 뒤, 성능 변경을 별도로 적용한다. (리팩토링과 성능 변경을 한 커밋에 섞지 않는다)

---

# 5. 개선 후(after)를 측정하고 before/after를 제시한다.
- before와 동일한 조건에서 after를 측정한다.
- before/after를 같은 단위로 나란히 제시한다. (예: p95 420ms → 180ms)
- 3단계 정확성 테스트가 여전히 모두 통과하는지 확인한다.
  - 정확성이 바뀌었다면 통과시키려 테스트를 고치지 말고 원인을 추적한다. 정확성 변경은 성능 개선의 일부가 아니다.
- 측정으로 정당화되지 않는(효과 없거나 미미한) 최적화는 적용하지 않고 되돌린다. 가독성 손해만 남기지 않는다.

---

# 6. 완료 후 정리한다.
- `부가내용.md` 절차에 따라 변경 이유·결과(before/after 수치 포함)와 외부 API 변경 여부를 기록한다.
- 트레이드오프가 있으면 명시한다. (예: 캐시 도입으로 응답시간↓ 대신 메모리↑·정합성 지연)

---

# 7. 언제 멈출지 정한다.
- 다음을 달성하면 멈춘다.
  - 목표 지표를 만족하고, 정확성 테스트가 모두 통과한다.
- 다음 경우에는 멈추고 사용자에게 보고한다.
  - 측정상 더 이상 의미 있는 병목이 없다. (남은 최적화는 효과 대비 비용이 큼)
  - 추가 개선이 정확성 변경이나 큰 아키텍처 변경을 요구한다.
  - 정확성을 고정할 테스트를 만들 수 없다.
