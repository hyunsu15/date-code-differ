# UX 가이드라인

## 순위

AppleUX가이드.md와 GoogleUX가이드.md를 읽고 학습한다.
AppleUI가이드.md와 GoogleUI가이드.md를 읽고 학습한다.

판단 시 아래 순서대로 적용한다.

1. **공식 (1순위)** — 각 가이드 본문 중 공식 문서(Apple HIG·developer.apple.com, Material Design `m3.material.io` 등)에서 확인된 내용을 가장 먼저 따른다.
2. **공식 내 충돌 해소** — 공식 내용끼리 충돌하면 UI는 Apple UI → Google UI 순서, UX는 Google UX → Apple UX 순서로 한다. **AppleUI 규칙과 Google(UI/UX) 규칙이 같은 요소에 대해 충돌하면 AppleUI를 따른다.**
3. **비공식 (최후 fallback)** — 위 1~2(공식 본문)로 판단할 수 없을 때만, 각 가이드 하단의 `비공식 (공식 문서 미수록)` 섹션을 참고한다. 공식 본문으로 결정할 수 있으면 비공식 섹션은 보지 않는다.
   - 단, 비공식 항목이 사람이 인지하기 어렵거나 보기 어려운 요소라면 그 값을 무시하고, 그렇게 판단한 이유와 대신 적용하는 방식을 안내한다.

### 주요 충돌 항목 확정 적용

| 항목 | AppleUI | Google (출처) | 적용 기준 |
| ---- | ------- | -------- | -------- |
| 애니메이션 목적 | 기능 설명용 금지, 상태 변화만 표현 | GoogleUX: 의미 있는 모션, 과도한 애니메이션 지양 | AppleUI 적용: 기능 설명용 금지 |
| 터치 영역 | 44×44pt 이상 (CSS에서는 44px) | GoogleUI: 48×48dp 이상 | AppleUI 적용: 44×44pt (=CSS 44px) |
| 그리드 단위 | 8pt(=CSS 8px) 배수 기준 | GoogleUI(Material): 4dp/8dp 그리드 | AppleUI 적용: 8px 배수 사용 |

> 위 수치의 공식 출처(Apple HIG / Material)는 `AppleUI가이드.md`·`GoogleUI가이드.md` 하단 "출처" 절을 참조. 출처가 명시되지 않은 세부 수치는 공식 미확인 값이다.

### @property CSS 변수 성능 주의

`transition: all`과 `var(--color)` 색상 변수를 함께 사용하면 렌더링 스레드가 멈추거나 트랜지션이 끊길 수 있다.
- 해결: 해당 CSS 변수를 `@property`로 타입 정의한다.
- 예외: 라이브러리가 지원하지 않거나 성능이 더 나빠지는 경우 적용하지 않는다.



## 1. 일관성 (Consistency)

같은 동작은 항상 같은 방식으로 동작해야 한다.

### 예시
- 삭제 버튼은 항상 빨간색
- 저장 버튼 위치 고정
- 모달 닫기 방식 통일
- 동일한 용어 사용
  - `회원` / `유저` 혼용 금지

### 목적
사용자가 학습한 패턴을 계속 활용 가능하게 만든다.

---

## 2. 가시성 (Visibility)

현재 상태를 사용자가 바로 이해할 수 있어야 한다.

### 예시
- 로딩 중 표시
- 저장 완료 토스트
- 현재 선택된 메뉴 강조
- 진행률 표시

### 안 좋은 예
- 버튼 눌렀는데 반응 없음
- 저장됐는지 안됐는지 모름

---

## 3. 피드백 (Feedback)

사용자 행동에 즉시 반응을 제공해야 한다.

### 예시
- 버튼 클릭 애니메이션
- hover 효과
- 성공/실패 메시지
- 입력 오류 표시

### 핵심
"내 행동이 시스템에 전달됐는가?"를 알려줘야 한다.

---

## 4. 단순성 (Simplicity)

복잡한 선택과 입력을 최소화한다.

### 예시
- 필수 입력만 요구
- 옵션 과도하게 노출하지 않기
- 한 화면에 너무 많은 정보 배치 금지

### 좋은 방식
- 자주 쓰는 기능 우선 배치
- 고급 옵션 접기

---

## 5. 오류 방지 (Error Prevention)

실수하기 어렵게 설계한다.

### 예시
- 삭제 전 확인 모달
- 저장 안 된 상태 이탈 경고
- 숫자만 입력 가능 처리
- 잘못된 날짜 선택 방지

### 핵심
에러 메시지보다 에러 자체를 안 나게 만드는 것이 중요하다.

---

## 6. 인지 부하 감소 (Reduce Cognitive Load)

사용자가 기억하거나 고민할 것을 줄인다.

### 예시
- 최근 검색 저장
- 자동완성
- 추천값 제공
- 이전 입력 유지

### 안 좋은 예
- 사용자가 규칙을 외워야 함
- 정보가 여러 화면에 분산됨

---

## 7. 접근성 (Accessibility)

누구나 사용할 수 있어야 한다.

### 예시
- 충분한 색 대비
- 키보드 조작 가능
- 스크린리더 대응
- 텍스트 크기 확보

### 대표 기준
- WCAG
- 모바일 터치 영역 최소 크기

---

## 8. 반응 속도 (Performance UX)

느린 서비스는 UX 자체를 망친다.

### 예시
- 클릭 후 즉시 시각 반응
- Skeleton UI 사용
- Lazy Loading
- 불필요한 렌더링 최소화

---

## 9. 정보 구조 (Information Architecture)

정보를 찾기 쉽게 구성한다.

### 예시
- 메뉴 깊이 최소화
- 관련 기능끼리 그룹화
- 검색 기능 제공

### 안 좋은 예
- 설정 위치가 예측 불가능
- 메뉴가 너무 깊음

---

## 10. 모바일 우선 고려 (Responsive UX)

화면 크기가 달라도 사용 가능해야 한다.

### 예시
- 터치 영역 확보
- 가로 스크롤 제거
- 작은 화면에서 우선순위 재배치

---

# 실무 UX 체크리스트

## 버튼(Button)
- 클릭 가능한지 명확한가?
- disabled 상태 이유가 보이는가?
- 중복 클릭 방지되는가?

---

## 폼(Form)
- 필수 입력 표시가 있는가?
- 에러 메시지가 이해 가능한가?
- 입력 중 validation 하는가?

---

## 테이블(Table)
- 정렬 가능한가?
- 검색 가능한가?
- 컬럼이 너무 많지 않은가?
- 모바일 대응이 되는가?

---

## 모달(Modal)
- ESC 닫기 가능한가?
- 바깥 클릭 닫기 정책이 일관성 있는가?
- 스크롤 충돌 없는가?

---

# 개발자 관점 UX 원칙

## 1. 사용자 기억보다 보여주기
외우게 하지 말고 UI로 안내한다.

---

## 2. 사용자 실수를 기본 전제로 설계
잘못 누를 수 있음을 가정한다.

---

## 3. 시스템 상태를 숨기지 말기
로딩 / 저장 / 실패 상태를 명확히 보여준다.

---

## 4. 기능보다 흐름 우선
기능이 많아도 흐름이 끊기면 UX는 나빠진다.

---
