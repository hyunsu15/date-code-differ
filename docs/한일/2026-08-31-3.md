# 2026-08-31 — SSH 비교가 느린 원인은 **접속 횟수**였다

## 왜

"SSH 로 파일 비교가 오래 걸린다" 를 따라가 보니 병목은 diff 계산도, 전송량도 아니었다.
**원격 명령 하나 = `ssh` 프로세스 하나 = TCP + 키교환 + 인증 한 번**인데, 그 명령을
파일 수만큼 띄우고 있었다.

- 좌우 비교: 파일 수 × 2 회. 그것도 `for...of await` 라 순차였다.
- 날짜 목록: 폴더마다 `find` 한 번 (N+1).

파일 500개면 왕복 500번. 접속 1회를 0.3초로 잡으면 150초인데, 실제 파일 바이트를
나르는 시간은 그중 몇 초도 안 된다.

접속 재사용(`ControlMaster`)은 답이 아니다. PowerShell 에서 뜨는 `ssh` 는
`C:\WINDOWS\System32\OpenSSH\ssh.exe`(OpenSSH_for_Windows 9.5p2)이고 다중화를 지원하지
않는다. 그래서 **재사용이 아니라 명령 수 자체를 줄이는** 쪽으로 갔다.

## 무엇을 했나

### 1. 본문을 한 번의 접속으로 몰아 읽는다 (`96b343d`)

소스 인터페이스를 전부 "여러 개를 한 번에" 모양으로 바꿨다
(`readFile`→`readFiles`, `listFiles`→`listFilesIn`). 원격 명령은 파일마다
`@@<바이트수>` 헤더 한 줄 + 그 길이만큼의 본문을 내보내고, 받는 쪽은 구분자를 찾지 않고
길이로 잘라 읽는다 — 본문에 무엇이 들어 있어도 안 깨지고, 경로를 출력에 싣지 않아
파일 이름으로 파싱이 흔들릴 자리도 없다. 없는 파일은 `@@-` 로 자리를 남긴다.

### 2. `cksum` 으로 같은 파일을 가려 한쪽만 받는다 (`feab7cb`)

목록을 만들던 `wc -c` 를 `cksum` 으로 바꿨다. POSIX 필수 유틸이라 Solaris·AIX 에도 있고,
출력이 `<CRC> <바이트수> <경로>` 라 **크기까지 한 줄에** 와서 왕복이 늘지 않는다.
좌우 체크섬이 같으면 한쪽만 받아 양쪽에 쓴다 — 전송량이 거의 절반이 된다.

읽기를 **아예 건너뛰지는 않았다.** 요약 카드가 동일한 파일의 총 줄 수·문자 수까지
합산해 보여주므로 본문 없이는 그 숫자를 채울 수 없다. 정확성을 지키면서 할 수 있는
일은 "두 번 받지 않기" 까지였다.

### 3. 날짜 목록을 한 명령으로 훑는다 (`bccf945`)

훑을 폴더를 `find` 에 한꺼번에 넘긴다(`find './2026-08-01' './2026-09-01' -type f -exec
cksum {} +`). 돌아온 경로의 첫 조각이 폴더 이름이라 받는 쪽에서 가르면 된다.
스냅샷 훑기 캐시도 배치로 바꿔(`scanSnapshots`) 좌우 비교의 스냅샷 조회가 2회→1회가 됐다.

## 결과

| 동작 | 전 | 후 |
| ---- | -- | -- |
| 날짜 목록 (폴더 30개) | 32회 | **2회** |
| 좌우 비교 (파일 500개) | 1,000회 | **7회** |
| 좌우 비교 전송량 | 양쪽 전부 | **같은 파일은 한쪽만** |

실측 수치는 아니다 — 접속 1회 단가는 서버·망마다 다르므로, 실제 개선폭은
`ssh <host> true` 를 10회 돌려 나온 단가에 위 횟수를 곱해서 본다.

## 검증

- 테스트 225개 통과 (기존 216 + 9).
- 실제 fixture 로 **체크섬 있는 소스와 없는 소스의 비교 결과가 `deepEqual` 로 완전히 같고**,
  읽기 횟수만 동일 파일 수만큼 줄어드는 것을 고정했다. 성능 개선이 요약 카드 숫자를
  바꿔 버리면 그건 버그다.
- 생성한 원격 명령을 로컬 `sh` 에 그대로 넣어 돌려, `cksum` 출력 형식과 `@@` 스트림
  프레이밍이 실제로 맞는지 확인했다 (없는 파일 자리 남기기 · 멀티바이트 경계 포함).

## 외부 API 변경

**없다.** 엔드포인트·파라미터·응답 형태가 그대로다
(`/api/v1/snapshots`, `/comparisons`, `/comparisons/files`).
바뀐 것은 서버 내부의 소스 계층 인터페이스뿐이라 화면 코드는 손대지 않았다.

## 남은 것

- 파일 본문 캐시가 없어 **무시 옵션을 토글할 때마다 원격을 다시 읽는다.**
  체크섬을 키로 쓰면 로컬 계산만으로 끝난다.
- `scanCache` · `comparisonCache` 는 상한 없는 메모리 Map 이고 재시작하면 날아간다.
  스냅샷은 불변이므로 디스크 캐시가 자연스럽다.
- 여기까지 오면 왕복이 아니라 **바이트**가 병목일 수 있다. 그때 `gzip -c` 를 재본다.

# 2026-08-31 (2) — 환경을 **좌우가 각각** 고른다 (운영 ↔ 테스트 비교)

## 왜

운영과 테스트를 견주고 싶다는 요구가 나왔다. 그런데 환경 선택이 화면에 **하나뿐**이라
두 환경을 동시에 볼 방법이 없었다.

"같은 날짜끼리만 비교" 로 좁힐 수도 있었지만 그러지 않았다. 환경을 폴더로 나눴다는 것
자체가 **배포 시점이 다르다**는 뜻이고, 같은 날짜 폴더가 양쪽에 다 있으리라는 보장이
없다. 정작 제일 자주 묻는 "지금 운영과 테스트가 얼마나 벌어져 있나" 는 각 환경의
**최신끼리** 견주는 질문이라, 같은 날짜로 묶으면 그 질문에 답을 못 한다.

별도 "환경 비교 모드" 도 만들지 않았다. 좌우가 각각 (환경, 날짜) 를 고르게 하면
기존 기능(같은 환경의 두 날짜)이 그 특수 케이스가 되고 모드 전환이 필요 없어진다.

## 무엇을 했나

### 1. 소스 계층: 비교는 좌우 위치를 따로 받는다

`compareSnapshots(source, cfg, key, left, right)` → `compareSnapshots(cfg, left, right)`.
좌우가 각각 `{ source, key, snapshotId }` 를 들고 온다. 캐시 키도 좌우 위치를 함께
넣어 JSON 으로 만든다 — 이어 붙이면 조합이 다른데 같은 키가 되는 자리가 생긴다.

**같은 위치면 훑기를 한 번으로 묶는다**(`scanBothSides`). 환경을 안 나누고 쓰는 흔한
경우에서 왕복이 늘지 않아야 해서다.

### 2. API: `rightRoot` 하나만 더 받는다

서버·계정·인코딩은 좌우가 같다(환경은 루트 아래 하위 폴더라는 전제). 갈리는 값은
위치뿐이라 **다를 때만** `rightRoot` 를 붙인다. 같은 환경을 볼 때는 URL 이 예전과 똑같다.

### 3. 순서 규칙을 조건부로

`이후 는 항상 이전보다 최신` 은 **좌우가 같은 위치일 때만** 성립한다. 운영 9/1 과
테스트 8/1 을 견주는 것은 거꾸로 된 비교가 아니라 "테스트가 뒤처져 있다" 는 정상적인
질문이다. `normalizeSelection` 이 `sameSource` 를 받아 두 규칙을 가른다.

### 4. 화면: 환경 선택이 날짜 칸 안으로

헤더의 `[운영][테스트]` 버튼 묶음을 없애고, 각 날짜 칸의 태그 자리에 환경 선택을 넣었다.
환경이 갈리면 그 자리 표시와 diff 창 머리가 `이전`/`이후` 대신 **환경 이름**이 된다 —
왼쪽이 더 최신일 수 있는데 "이전" 이라 부르면 거짓말이 되기 때문이다.

날짜가 없어도 환경 선택은 잠그지 않는다. 잠그면 빈 환경에서 빠져나갈 수가 없다.

저장값은 좌우 한 쌍이 됐고, 예전 저장값(환경 하나)은 **양쪽 다 그 환경**으로 읽는다.

## 검증

- 테스트 237개 통과 (기존 225 + 12). 좌우가 다른 위치인 비교·본문 읽기·캐시 분리와,
  순서 규칙이 환경에 따라 갈리는 것을 고정했다.
- 브라우저에서 네 조합을 직접 확인했다: 운영↔운영 / 운영→테스트(같은 날짜) /
  운영 9-01 → 테스트 8-01(왼쪽이 더 최신) / 테스트↔테스트.
  같은 환경으로 되돌리면 순서 규칙이 다시 걸려 선택이 자동으로 바로잡히는 것까지 봤다.
- 요청 URL 확인: 환경이 같을 때는 `rightRoot` 가 붙지 않는다.

## 외부 API 변경

**있다.** 비교 두 엔드포인트에 선택 파라미터 `rightRoot` 가 생겼다.

| 엔드포인트 | 변경 |
| --- | --- |
| `GET /api/v1/comparisons` | `rightRoot` (String, 선택) 추가 |
| `GET /api/v1/comparisons/files` | `rightRoot` (String, 선택) 추가 |
| `GET /api/v1/snapshots` | 변경 없음 (한 번에 한 위치. 좌우가 다르면 화면이 두 번 부른다) |

**하위 호환된다.** 없으면 예전처럼 양쪽 다 `root` 를 본다. 응답 형태는 그대로다.

## 남은 것

- `/snapshots` 는 여전히 한 번에 한 위치다. 좌우가 다른 환경이면 요청이 2회다 —
  같은 호스트라면 base root 에서 한 번에 훑을 수 있지만, 지금은 root 가 이미 환경까지
  내려가 있어 구조를 더 건드려야 한다. 2회는 부담이 아니라 두지 않았다.
- 요약 카드의 `이전 총 줄 수` · `이후 총 줄 수` 문구는 그대로다. 툴팁에 환경 이름이
  들어가 오해는 없지만, 문구 자체를 중립적으로 바꾸는 건 별도 건으로 남긴다.

# 2026-08-31 (3) — 환경 라벨에 색을 준다

## 왜

운영과 테스트를 나란히 놓으면 **이름만으로는 잘 안 걸린다.** 잘못된 쪽을 보고 있는 걸
모른 채 판단하면 그대로 사고다. 색이 붙어야 읽기 전에 눈에 먼저 들어온다.

## 무엇을 했나

- 운영 = **주황**(`#f0883e`), 테스트 = **하늘색**(`#79c0ff`). 라이트 테마는 배경에 묻지
  않게 글자를 진하게 따로 잡았다.
- **빨강·초록은 안 쓴다.** 이 화면에서 그 둘은 이미 삭제·추가라는 뜻이라, 운영 태그를
  녹색으로 두면 왼쪽에 놓였을 때 "추가됨" 으로 읽힌다.
- 색은 환경 **이름이 아니라 `ENV_FOLDERS` 순서**로 정한다. 환경 이름은 프로젝트마다
  달라(`prod` · `stage` · `운영`) 이름에 색을 박아 둘 수가 없다. 4개까지 준비하고 넘으면 돈다.
- **색은 글자를 따라간다.** 환경 이름이 쓰여 있으면 환경 색, `이전`/`이후` 면 좌/우 색이다.
  그래서 좌우가 같은 환경일 때 diff 창 머리는 예전처럼 빨강·초록으로 남는다 —
  글자와 색이 서로 다른 것을 가리키면 안 된다.

## 검증

- 테스트 240개 통과 (237 + 3). 환경끼리 색이 겹치지 않는 것, 순서대로 붙는 것,
  없는 id 는 색을 안 받는 것을 고정했다.
- 브라우저에서 다크·라이트 양쪽의 실제 계산된 색을 확인했고, 같은 환경일 때
  diff 창 머리가 빨강·초록으로 되돌아가는 것도 봤다.

## 외부 API 변경

**없다.** 화면 표시만 바뀌었다.

# 2026-08-31 (4) — 사용설명서에 스크린샷을 넣고 낡은 설명을 고친다

## 왜

`ai/부가내용.md` 의 사용설명서 규칙 중 **지켜지지 않은 것이 스크린샷**이었다. 글만
500줄이라 "그 버튼이 화면 어디에 있는지" 를 읽는 사람이 상상해야 했다.

더 급한 건 따로 있었다. 최근 작업 때문에 **설명이 사실과 달라진 곳이 세 군데** 있었다.
설명서가 틀린 말을 하면 없는 것보다 나쁘다.

| 어디 | 뭐가 틀렸나 |
| --- | --- |
| SSH 접속 횟수 표 | "파일 200개면 400번" → 지금은 파일 200개당 2번 |
| "같은 날짜를 고르고 싶습니다" | "고를 수 없습니다" → 환경이 다르면 된다 |
| "이전과 이후를 서로 바꾸고 싶습니다" | "바꿀 수 없습니다" → 환경이 다르면 된다 |

## 무엇을 했나

### 1. 캡처를 자동화했다 (`npm run shots`)

개발 서버가 서빙하는 `scripts/shot.html` 이 앱을 iframe 으로 띄운다. **같은 출처**라
iframe 안의 실제 요소 좌표를 읽어 그 위에 빨간 박스와 번호를 그린다. 좌표를 손으로
적어 두면 UI 가 조금만 움직여도 박스가 엉뚱한 데를 가리키는데, 그럴 일이 없다.

이미 깔린 Chrome·Edge 를 헤드리스로 띄워 찍는다. Playwright 는 브라우저만 수백 MB라
받지 않았다.

**버튼 하나만 잘라 찍지 않는다.** 화면 전체를 담고 그 위에 번호를 얹는다 —
부가내용.md 의 캡처 규칙 그대로다.

### 2. 그림 6장을 넣었다

화면 한눈에 보기 · 위치 설정 · 비교할 곳 고르기 · 운영↔테스트 · 파일 고르기 · 코드 비교.
각 그림 옆에 ①②③ 표를 붙여 무엇이 무엇인지 짚었다.

### 3. 주요 흐름을 행동 중심으로 바꿨다

> ⚙ 위치 클릭 ➡️ 내 PC 폴더 클릭 ➡️ 폴더 경로 확인 ➡️ 적용 클릭

### 4. 낡은 설명 세 군데를 고쳤다

위 표의 세 가지. "고를 수 없다/바꿀 수 없다" 는 **같은 환경일 때만** 맞는 말이라
조건을 붙이고, 환경이 다르면 되는 경우를 예시와 함께 적었다.

## 검증

- 그림 6장을 `npm run shots` 로 전부 다시 뽑아 재현되는 것을 확인했다.
- 설명서가 참조하는 이미지 경로 6개가 실제 파일과 맞는지 확인했다.
- 테스트 240개 통과, 빌드 정상.

## 외부 API 변경

**없다.** 문서와 캡처 스크립트만 늘었다.
