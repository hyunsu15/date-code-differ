# 2026-10-27 — 스키마 덤프를 PC 에서 떠서 서버에 올리는 쉘 스크립트 (`shl/`)

## 왜

- 스키마 덤프 txt 를 사람이 DB 툴에서 내보내 손으로 올리고 있었다 — 이름 · 형식을 틀리면 화면이 그 날짜를 못 읽는다.
- DB 는 **내 PC 에서만** 붙고 서버는 DB 에 못 붙는다. 그래서 조회는 PC, 서버는 파일만 받는 구조로 했다.
- 웹 도구(배포본)는 서버에서 돌고 DB 에 못 붙으므로 API · 버튼으로 넣지 않았다 — 별도 쉘 스크립트로 분리 (사용자 요청).

## 무엇을 했나

- `shl/install-oracle-client.sh` — Instant Client **19.32**(basic + sqlplus)를 `shl/oracle/` 에 압축 해제. SHA256 확인.
  19 를 고른 이유: DB 버전 미확인 상태에서 11.2 ~ 21c 까지 붙는다 (23 은 19c 이상만).
- `shl/schema-dump.sh <환경> [날짜] [--force]` — USER_*(또는 `DB_OWNER` 지정 시 ALL_*) 딕셔너리를 화면 파서 형식
  (`[COLUMN]` · `[CONSTRAINT]` · `[INDEX]` + 헤더)으로 뽑아 `shl/out/` 에 저장 → ssh 한 번으로 업로드.
  비밀번호는 매번 묻고 sqlplus 에 표준입력으로만 넘긴다. 같은 이름은 덮어쓰지 않고, 임시 이름 → mv 로 교체.
- 설정은 `shl/schema-dump.env` (SSH · DB 접속 · 원격 폴더 · 파일 이름 규칙)로 분리, `.gitignore` 에 env · oracle · out 추가.
- 실제로 부딪힌 것: Git Bash 가 `/nolog` 를 윈도우 경로로 바꿔 sqlplus 가 사용법만 찍음 → `MSYS_NO_PATHCONV=1`.
  sqlplus 는 접속 실패(ORA-12154)에도 **종료 코드 0** 으로 끝남 → 출력의 `ORA-` · `SP2-` 로도 실패를 가린다.
- 테스트: `schemaDump.test.ts` 13건 — sqlplus · ssh 만 가짜로 두고 진짜 스크립트를 돌려 결과 파일을 `parseSchema` 로 읽힘.
  덮어쓰기 거부 / --force, ORA · SP2 오류, 테이블 0개, OWNER 주입 차단, 공백 · 작은따옴표 경로, 업로드 실패 시 파일 보존 등.
  테스트에서 잡은 스크립트 버그 2건(기본 파일명 `}` 확장, 0건일 때 pipefail 로 무안내 종료) 수정. 전체 540개 통과.
- 실제 DB 접속은 확인 못 함 — 접속 정보가 아직 없다. 진짜 sqlplus 로 접속 실패 경로까지만 확인.
- README(덤프 만들기 · 폴더 구조 · 알아둘 점), 사용설명서 7-8 절.

# 2026-10-27 — 윈도우에서 Git Bash 없이 부르는 래퍼 (`shl\*.cmd`)

- 사용자 요청: 윈도우에서 주로 쓰는데 Git Bash 를 여는 게 번거롭다. `.ps1` 대신 `.cmd` 로 했다 —
  윈도우 기본 실행 정책(Restricted)에서 `.ps1` 은 막히고 `.cmd` 는 안 막힌다. 로직은 `.sh` 한 벌, 래퍼는 Git 의 bash 로 부르기만 한다.
- 함정 두 개를 래퍼에서 처리: PATH 의 `bash` 는 WSL 일 수 있어 Git 설치 위치에서 찾고, `\` 경로는 bash 의 dirname 이
  못 읽어 `/` 로 바꿔 넘긴다 (안 바꾸면 스크립트가 자기 폴더를 못 찾아 엉뚱한 곳에 설정을 만든다).
- `.gitattributes` 신설: `core.autocrlf=true` 인데 없어서, 다른 윈도우 PC 에서 받으면 `.sh` 가 CRLF 가 되어 bash 가 죽을 수 있었다
  (기존 `update.sh` · `rollback.sh` 도 해당). `*.sh` LF · `*.cmd` CRLF 고정.
- 확인: PowerShell · cmd · 다른 폴더에서 호출, 인자 · 종료 코드 전달. 테스트 2건 추가(래퍼 인자 · 종료 코드, change/ 찾기) — 15건 통과.
- 외부 API 변경: 없음.

# 2026-10-27 — 조회 SQL 을 `change/check_table.sql` 로 분리

- 사용자 요청: 스크립트 안의 SELECT 를 파일로 빼서 고칠 수 있게. SELECT · PROMPT 헤더만 파일에 두고,
  형식을 정하는 SET · WHENEVER · 접속은 스크립트에 남겼다 (바꾸면 화면이 못 읽는다). **커밋하는 파일** — 팀이 같은 쿼리로 떠야 한다.
- USER_* / ALL_* 를 스크립트가 바꿔 끼우던 것을 `ALL_* + '&owner'` 하나로 통일. `&owner` = DB_OWNER, 비었으면 접속 계정(대문자).
- 막은 것: `&owner` 외 치환 변수(sqlplus 가 다음 SQL 줄을 값으로 삼킴), 메모장 BOM(첫 줄 SP2-0734) · CRLF, SQL 파일 없음.
- 고친 것: `WHENEVER` 를 CONNECT 앞으로 — 뒤에 있으면 접속 실패에도 sqlplus 가 0 으로 끝났다(실제 sqlplus 로 확인, 이제 1).
- 테스트 6건 추가·교체 — 20건 통과. 실제 sqlplus(/nolog)로 SQL 파일이 프롬프트 없이 끝까지 해석되는 것 확인.
- 외부 API 변경: 없음.

# 2026-10-27 — SQL 중간 빈 줄에서 `SP2-0734 … rest of line ignored`

- 사용자 제보: ORDER BY 앞에 빈 줄이 있는 쿼리에서 "rest of line ignored". sqlplus 는 기본(SQLBLANKLINES OFF)으로
  빈 줄에서 문장을 끊어, SELECT 는 실행되지 않고 ORDER BY 줄이 모르는 명령이 된다. 실제 sqlplus 로 재현.
- `SET SQLBLANKLINES ON` 을 스크립트 머리에 추가 — DB 툴처럼 `;` 까지를 한 문장으로 읽는다. 같은 입력이 끝까지 실행 단계에 닿는 것 확인.
- SQL 파일 머리 주석 · 사용설명서에 "빈 줄 괜찮음, `;` 는 필수" 추가. 테스트 20건 통과.
- 외부 API 변경: 없음.

# 2026-10-27 — 빌드 · 옮기기 · 서버 명령을 한 번에 하는 배포 스크립트 (`shl/deploy.sh` · `deploy.cmd`)

- 사용자 요청: 빌드 → ssh 로 빌드 파일 옮기기 → 서버에서 명령 실행을 cmd 하나로. SSH · 빌드 · 명령 등 바뀔 수 있는 값은 설정 파일로 분리.
  로직은 `.sh` 한 벌, `.cmd` 는 기존 `_git-bash.cmd` 로 부르기만 한다 (스키마 덤프와 같은 구조).
- 설정 `change/deploy.env`(커밋 안 함, `.gitignore`) · 템플릿 `shl/deploy.env.example` — 스키마 덤프와 같은 배치.
  처음엔 `change/env/` 폴더로 했다가, 아직 파일이 적어 폴더까지는 필요 없다는 사용자 의견으로 되돌림.
  값: `SSH_*` · `BUILD_CMD` · `BUILD_DIR` · `DEPLOY_FILES` · `REMOTE_DIR` · `REMOTE_CMD`. 옵션 `--skip-build` · `--no-run`.
- 전송은 `tar | ssh` — 서버의 임시 폴더에 다 풀린 뒤에만 바꿔 끼워, 끊겨도 기존 파일이 남는다. `DEPLOY_FILES` 는 서버에서 `rm -rf` 하는
  이름이라 맨 위 단계 이름만 받는다 (`/` · `..` 차단). 빌드 실패 · 옮길 것 없음이면 서버에 붙지 않는다.
- 테스트: `deploy.test.ts` 14건 — 빌드 · ssh 만 가짜로 두고 진짜 스크립트와 진짜 `update.sh` 를 돌림. 전송 중단, 경로 차단, 공백 · 따옴표 폴더,
  서버 명령 실패 시 롤백 안내, 래퍼 등. 전체 561개 통과, 타입 검사 통과. PowerShell 에서 `shl\deploy.cmd` 직접 실행 확인.
- 실제 서버 배포는 확인 못 함 — 서버 정보 · 재시작 방법(pm2 · systemd 등)을 모른다. `REMOTE_CMD` 기본은 `bash update.sh` 까지.
- 외부 API 변경: 없음. 웹 도구와 별개로 돈다.
